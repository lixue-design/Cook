# 人员分工与 Harness 落地规划

本文结合产品设计文档、MVP 范围和工程方案，确认菜谱小程序 MVP 阶段的人员分工与 Harness Engineering 落地方式。

## 1. 结论

MVP 阶段建议采用“小团队 + 强 Harness”的模式：

- **PM/产品负责人**守范围、验收和合规。
- **Tech Lead**守架构、模块边界、Harness 规则和代码评审。
- **小程序前端**负责页面、组件、微信能力和前端体验。
- **后端研发**负责真实数据闭环、业务规则、鉴权、上传、计划和菜篮服务。
- **QA/验收负责人**负责测试用例、验收清单、提审前回归。
- **Agent/Codex**作为受控执行者，适合做模块内实现、测试补齐、文档同步和重复性改造。

核心原则：**产品设计决定范围，Harness 决定执行轨道，代码实现必须被 spec、任务卡、测试和 review checklist 约束。**

## 3. 团队配置

### 3.1 推荐配置

| 角色 | 人数 | 主要职责 |
| --- | --- | --- |
| PM/产品负责人 | 1 | 产品范围、需求澄清、优先级、验收标准、合规文案。 |
| UI/UX | 0.5-1 | 页面原型、视觉规范、关键交互、空态/错误态。 |
| 小程序前端 | 1-2 | 页面、组件、微信登录调用、图片选择压缩、本地草稿、联调。 |
| 后端研发 | 1-2 | API、数据库、鉴权、上传、计划生成、菜篮合并、部署。 |
| QA | 0.5-1 | 测试用例、回归、提审前验收、缺陷管理。 |
| Tech Lead | 0.5 | 架构决策、Harness 维护、任务拆解、PR review。 |
| Agent/Codex | 按需 | 任务内实现、测试、文档同步、代码审查辅助。 |

### 3.2 最小配置

| 角色 | 人数 | 兼任建议 |
| --- | --- | --- |
| PM/设计/验收 | 1 | 负责产品、原型、文案、验收。 |
| 全栈/后端 | 1 | 负责服务端、数据、部署、接口。 |
| 小程序前端 | 1 | 负责页面、组件、微信能力、联调。 |
| Agent/Codex | 按需 | 承担文档、测试、局部实现，提高吞吐。 |

最小配置下，必须严格控制 MVP 范围，不插入 AI 生成、月计划、运营后台。

## 6. 任务拆解规划

### 6.2 任务卡要求

每个任务卡必须包含：

- 背景和目标。
- 包含/不包含范围。
- 必读上下文。
- API/数据变更。
- 验收标准。
- 测试要求。
- 完成汇报模板。

Agent 只能在任务卡边界内执行，发现边界不清时先补问题，不直接扩展实现。

## 7. 迭代节奏

### 第 0 阶段：Harness 对齐

目标：让团队和 Agent 有共同工作轨道。

交付：

- 人员分工确认。
- 任务卡第一批。
- 本地启动和验证说明。
- OpenAPI/API 契约初版。
- 模块 owner 表。

### 第 1 阶段：菜谱真实闭环

目标：从 mock 走向真实数据。

交付：

- 菜谱 CRUD 接口。
- 分类 CRUD 接口。
- 图片上传接口。
- 小程序菜谱列表/详情/编辑接入真实 API。
- 菜谱模块测试和冒烟。

### 第 2 阶段：计划真实闭环

目标：计划不再只是页面态或本地态。

交付：

- 日计划接口。
- 计划菜谱快照。
- 周计划生成规则。
- 计划页接入真实 API。
- 删除菜谱后计划快照验证。

### 第 3 阶段：菜篮真实闭环

目标：菜篮从计划快照生成并可持久化。

交付：

- 菜篮同步接口。
- 食材合并规则。
- 勾选、手动新增、删除持久化。
- 菜篮页接入真实 API。

### 第 4 阶段：合规与提审

目标：达到小程序提审和内测标准。

交付：

- 登录态完整闭环。
- 协议、隐私、注销入口。
- MVP 验收清单全部跑完。
- PR checklist 无 P0 风险。

## 8. 人与 Agent 的协作边界

### 8.1 适合交给 Agent

- 按 spec 实现明确接口。
- 写数据校验和纯函数。
- 写单元测试和测试样例。
- 替换 mock 为 API client。
- 补空态、失败态、加载态。
- 更新文档和任务卡。
- 做局部代码审查。

### 8.2 不建议直接交给 Agent

- 未确认产品范围的功能。
- 微信审核策略判断。
- 大规模架构迁移。
- 生产配置、密钥、权限开通。
- 与真实支付、合规、删除用户数据相关的不可逆操作。
- 没有验收标准的“优化一下”。

### 8.3 Agent 每次交付必须说明

- 读了哪些上下文。
- 改了哪些文件。
- 覆盖哪些验收点。
- 跑了哪些测试。
- 哪些风险未覆盖。

## 9. Review 机制

每个 PR 至少过三道关：

1. **范围关**：PM/Tech Lead 确认没有越过 MVP。
2. **规则关**：Tech Lead 确认快照、合并、鉴权、数据隔离没有破坏。
3. **验收关**：QA 或模块负责人确认测试和手动冒烟完成。

重点审查项：

- 是否仍依赖 mock/globalData 冒充真实闭环。
- 是否把计划生成、菜篮合并只写在前端。
- 是否新增了不在 MVP 的 AI/月计划/运营后台能力。
- 是否提交了真实密钥、临时地址或本地私有配置。
- 是否缺少错误态和保存失败兜底。

## 10. 当前确认建议

基于产品设计文档，当前推荐确认如下：

- **MVP 负责人**：PM。
- **技术总负责人**：Tech Lead。
- **前端主战场**：菜谱页、计划页、菜篮页、我的页。
- **后端主战场**：用户、菜谱、计划、菜篮、上传、协议。
- **第一优先级**：把现有页面能力接到真实 API 和持久化数据。
- **第二优先级**：补齐计划快照和菜篮合并的服务端规则。
- **第三优先级**：补齐登录合规与提审检查。
- **暂缓**：AI 生成菜谱、月计划、运营后台、复杂历史复刻。

下一步应先生成第一批任务卡，然后按菜谱真实闭环、计划真实闭环、菜篮真实闭环推进。
