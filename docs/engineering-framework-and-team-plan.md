# 菜谱小程序工程框架与人员分工

本文承接 [MVP 范围与实现拆解](./mvp-scope-and-implementation-breakdown.md)，目标是定义首版工程架构、模块边界、协作方式和人员分工，让团队可以进入建仓、排期、开发和验收阶段。

## 1. 工程目标

### 1.1 首版交付目标

在 4-6 周内完成一个可内测、可提交小程序审核的 MVP：

- 微信登录与用户体系。
- 菜谱分类、菜谱创建、编辑、删除、详情。
- 日计划、周计划生成和手动调整。
- 周菜篮汇总、勾选、手动维护。
- 我的页、协议页、注销申请入口。

### 1.2 工程原则

- 前后端边界清晰，业务规则尽量沉到服务端。
- 小程序端优先保证交互体验和离线草稿，不承载复杂计划生成逻辑。
- 计划和菜篮使用快照模型，避免历史数据被菜谱编辑污染。
- AI 能力、运营后台、月计划先预留扩展点，不进入首版主链路。
- 接口和数据模型先稳定，UI 可以迭代。

## 2. 推荐技术架构

### 2.1 总体架构

```text
微信小程序
  |
  | HTTPS API
  v
API 服务
  |
  |--------------------|
  v                    v
关系型数据库           对象存储
MySQL/PostgreSQL       菜谱封面/步骤图片
  |
  v
任务/规则模块
周计划生成、菜篮汇总、账号注销处理
```

### 2.2 技术选型建议

| 层级 | 推荐选型 | 说明 |
| --- | --- | --- |
| 小程序端 | 微信小程序原生 + TypeScript | 首版最贴近微信能力，审核和登录链路最少绕路。 |
| UI 组件 | 自建轻量组件 + 少量成熟组件库 | 菜谱卡片、餐段、菜篮项建议自建，避免 UI 风格被组件库绑死。 |
| 状态管理 | 页面状态 + 轻量全局 store | MVP 状态不复杂，避免过早引入重型方案。 |
| 服务端 | Node.js + NestJS 或 Go + Gin | 二选一即可；如果团队前端/全栈多，优先 Node.js；后端 Go 经验强则用 Go。 |
| ORM/数据访问 | Prisma/TypeORM 或 GORM | 统一 migration、模型和查询规范。 |
| 数据库 | MySQL 或 PostgreSQL | 关系型数据适合菜谱、计划、菜篮结构。 |
| 缓存 | Redis 后置 | MVP 不强依赖，可用于登录态、限流、热点配置。 |
| 图片存储 | 对象存储 | 存菜谱封面、步骤图，数据库只存 URL 和元信息。 |
| 文档 | Markdown + OpenAPI | `docs/` 存产品和工程文档，接口用 OpenAPI 管理。 |

### 2.3 首版推荐组合

如果团队没有强约束，建议采用：

```text
微信小程序原生 TypeScript
Node.js + NestJS
Prisma
PostgreSQL 或 MySQL
对象存储
OpenAPI
```

原因：

- 小程序原生降低微信登录、上传、审核风险。
- NestJS 模块边界清晰，适合按业务域拆分。
- Prisma migration 适合早期快速迭代数据模型。
- OpenAPI 方便前后端并行和 mock。

## 4. 服务端模块设计

### 4.1 模块划分

| 模块 | 职责 | 关键接口 |
| --- | --- | --- |
| `auth` | 微信登录、退出、token/session 管理 | `/api/auth/wechat-login`、`/api/auth/logout` |
| `users` | 当前用户、账号状态、注销申请 | `/api/me`、`/api/account/cancel-request` |
| `categories` | 菜谱分类 CRUD 和排序 | `/api/recipe-categories` |
| `recipes` | 菜谱 CRUD、食材、步骤、删除校验 | `/api/recipes` |
| `uploads` | 图片上传、格式/大小校验、对象存储 | `/api/uploads/recipe-image` |
| `plans` | 日计划、周计划、计划菜谱快照、生成规则 | `/api/week-plans`、`/api/day-plans` |
| `baskets` | 周菜篮、食材合并、勾选、手动维护 | `/api/baskets` |
| `agreements` | 协议正文、版本 | `/api/agreements` |

### 4.2 业务规则归属

| 规则 | 放置位置 | 原因 |
| --- | --- | --- |
| 菜名长度、耗时/热量范围 | 前端 + 后端双校验 | 前端体验，后端兜底。 |
| 食材解析与合并 | 后端 | 保证菜篮生成一致。 |
| 周计划生成 | 后端 | 便于后续替换为 AI 或更复杂规则。 |
| 计划快照生成 | 后端 | 避免前端构造不完整快照。 |
| 图片大小/格式校验 | 前端 + 后端双校验 | 前端提前拦截，后端安全兜底。 |
| 草稿缓存 | 小程序端 | 属于单设备编辑体验。 |
| 协议版本校验 | 后端主导 | 登录和合规状态需要服务端记录。 |

### 4.3 服务端分层

```text
Controller   # 处理 HTTP、参数解析、权限注解
Service      # 业务流程编排
Domain       # 计划生成、食材合并等纯业务规则
Repository   # 数据访问
DTO/Schema   # 入参出参校验
```

示例：

```text
plans/
  plans.controller.ts
  plans.service.ts
  domain/
    week-plan-generator.ts
    recipe-tagger.ts
  repositories/
    plans.repository.ts
  dto/
    generate-week-plan.dto.ts
```

### 5.2 前端职责边界

| 模块 | 前端职责 |
| --- | --- |
| 登录 | CloudBase 函数上下文解析可信微信身份；小程序展示协议勾选并保存非敏感本地用户态，不自行保存 AppSecret 或另造 session。 |
| 菜谱编辑 | 表单交互、本地草稿、图片选择/压缩、基础校验。 |
| 菜谱列表 | 分类筛选、分页加载、空态和加载态。 |
| 周计划 | 展示生成结果、覆盖确认、进入日计划。 |
| 日计划 | 三餐操作、选择菜谱、移除菜谱。 |
| 菜篮 | 勾选、手动新增、删除、同步提示。 |
| 我的 | 用户信息、协议、退出登录、注销申请入口。 |

### 5.3 前端状态策略

- 用户信息：全局 store。
- 当前 Tab 数据：页面内状态，进入页面刷新。
- 菜谱编辑草稿：本地 storage，按 `recipeDraft:{recipeId|new}` 存储。
- 周计划/菜篮：服务端为准，前端只做乐观更新，失败回滚。
- 登录失效：统一请求拦截器处理，跳转登录页。

## 6. 数据与一致性设计

### 6.1 快照策略

计划中保存菜谱快照：

- 菜谱名称
- 封面图
- 耗时
- 热量
- 食材
- 原菜谱 ID

这样可以保证：

- 菜谱编辑后，不影响已生成计划。
- 菜谱删除后，历史计划仍可展示。
- 菜篮从计划快照生成，而不是实时读取菜谱最新版本。

### 6.2 菜篮同步策略

MVP 默认使用 `replace_plan_items`：

- 删除旧的计划来源菜篮项。
- 保留用户手动新增项。
- 重新从当前周计划快照汇总食材。
- 同名同单位数字用量自动求和。
- 同名不同单位分行展示。

### 6.3 删除策略

| 对象 | MVP 策略 |
| --- | --- |
| 菜谱 | 软删除，历史计划保留快照。 |
| 分类 | 硬删除或软删除均可，分类下菜谱转入未分类。 |
| 计划项 | 硬删除，历史操作日志后置。 |
| 菜篮项 | 硬删除，手动项删除后不恢复。 |
| 用户 | 注销申请先记录状态，实际清理通过后台脚本或人工流程处理。 |

## 7. 环境与发布

### 7.1 环境划分

| 环境 | 用途 | 数据 |
| --- | --- | --- |
| local | 本地开发 | 本地数据库或共享测试库。 |
| dev | 联调环境 | 可随时重置。 |
| staging | 提审/验收环境 | 接近生产配置，保留稳定测试数据。 |
| prod | 线上环境 | 正式用户数据。 |

### 7.2 配置项

| 配置 | 说明 |
| --- | --- |
| `WECHAT_APP_ID` | 小程序 AppID。 |
| `WECHAT_APP_SECRET` | 小程序密钥，仅服务端保存。 |
| `DATABASE_URL` | 数据库连接。 |
| `OBJECT_STORAGE_BUCKET` | 图片存储桶。 |
| `OBJECT_STORAGE_REGION` | 图片存储区域。 |
| `JWT_SECRET` 或 `SESSION_SECRET` | 登录态签名密钥。 |
| `MAX_IMAGE_SIZE_MB` | 图片大小限制，默认 5MB。 |

### 7.3 发布流程

```text
需求冻结 -> 开发分支 -> 自测 -> 联调 -> QA 测试 -> staging 验收 -> 小程序体验版 -> 提审 -> 发布
```

关键门禁：

- 数据库 migration 已执行。
- OpenAPI 与前端客户端已同步。
- 核心接口有单元测试或集成测试。
- 小程序端完成主流程冒烟。
- 协议、隐私、注销入口可访问。

## 8. 质量保障

### 8.1 测试分层

| 类型 | 负责人 | 范围 |
| --- | --- | --- |
| 单元测试 | 后端/前端 | 食材合并、周计划生成、表单校验、日期工具。 |
| 接口测试 | 后端/QA | 登录、菜谱、计划、菜篮主接口。 |
| 页面测试 | 前端/QA | 页面跳转、空态、加载态、失败态。 |
| 端到端测试 | QA 主责 | 新建菜谱 -> 生成计划 -> 同步菜篮 -> 勾选采购。 |
| 审核检查 | PM/QA | 协议、隐私、授权文案、注销入口。 |

### 8.2 必测主链路

1. 首次登录并同意协议。
2. 新建带图片、食材、步骤的菜谱。
3. 编辑菜谱后查看详情。
4. 生成本周计划。
5. 手动调整某日午餐。
6. 从周计划同步菜篮。
7. 勾选采购项并手动新增食材。
8. 删除菜谱后查看历史计划快照。
9. 退出登录后重新登录。
10. 进入协议和注销申请页面。

### 8.3 工程规范

- API 返回统一结构：`code`、`message`、`data`、`requestId`。
- 服务端所有写接口需要鉴权。
- 所有用户数据表必须带 `user_id`。
- 时间统一存 UTC 或服务端标准时间，前端展示按本地时区格式化。
- 删除用户生成内容优先软删除，除非明确不需要恢复。
- 图片上传只允许 JPG、PNG、WebP。
- 接口字段命名前后端统一使用 camelCase，数据库使用 snake_case。

## 9. 人员分工

### 9.1 标准配置

| 角色 | 人数 | 职责 |
| --- | --- | --- |
| 产品经理 | 1 | 需求收敛、优先级、验收标准、审核材料。 |
| UI/UX 设计 | 0.5-1 | 页面原型、视觉规范、空态/错误态、交互细节。 |
| 小程序前端 | 1-2 | 小程序页面、组件、微信能力、联调、自测。 |
| 后端研发 | 1-2 | API、数据库、业务规则、图片上传、部署。 |
| QA 测试 | 0.5-1 | 测试用例、功能测试、回归、提审前检查。 |
| 技术负责人 | 0.5 | 架构把关、任务拆解、代码评审、风险处理。 |
| 运营/内容 | 0.2 | 内置菜谱/协议文案/测试数据，可由 PM 兼任。 |

### 9.2 最小可行团队

如果资源紧张，最低配置可以是：

| 角色 | 人数 | 兼任方式 |
| --- | --- | --- |
| PM/设计 | 1 | 产品、原型、验收、文案。 |
| 全栈/后端 | 1 | 后端、数据库、部署、接口文档。 |
| 小程序前端 | 1 | 小程序、组件、联调、自测。 |
| QA | 0.3 | 由 PM + 研发交叉测试，关键节点集中测试。 |

这种配置建议把首版控制在 4-5 周，不要同时做 AI 和运营后台。

## 11. 里程碑排期

以 5 周为基准，可按团队人数压缩或拉长。

### 第 0 周：启动与冻结

交付物：

- MVP 范围冻结。
- 页面清单和主流程确认。
- 数据模型初版。
- OpenAPI 初版。
- 工程仓库初始化。

负责人：

- PM 负责范围和验收。
- 技术负责人负责架构和任务拆解。
- 前后端完成工程初始化。

### 第 1 周：基础工程与菜谱 CRUD

交付物：

- 小程序基础框架、Tab、请求封装。
- 后端登录、用户、分类、菜谱基础接口。
- 菜谱列表、详情、新建/编辑基础页面。
- 图片上传链路跑通。

### 第 2 周：菜谱编辑完善与计划基础

交付物：

- 食材编辑器、步骤编辑器、草稿机制。
- 分类管理。
- 日计划数据模型和接口。
- 周计划生成规则初版。
- 选择菜谱页。

### 第 3 周：计划闭环与菜篮闭环

交付物：

- 周计划页、日计划页。
- 添加/移除餐段菜谱。
- 计划快照。
- 菜篮同步、合并、勾选、手动新增/删除。

### 第 4 周：合规、体验与测试

交付物：

- 我的页、协议页、注销申请页。
- 空态、错误态、加载态完善。
- QA 第一轮完整测试。
- 修复 P0/P1 问题。

### 第 5 周：提审准备与灰度

交付物：

- 小程序体验版。
- 审核材料和协议文案确认。
- 回归测试完成。
- 上线 checklist 完成。
- 内测用户反馈收集机制。

## 12. 模块开发优先级

### P0：必须完成

- 微信登录
- 菜谱分类
- 菜谱 CRUD
- 图片上传
- 日计划
- 周计划生成
- 菜篮同步和勾选
- 协议页、隐私政策、退出登录、注销入口

### P1：强烈建议完成

- 本地草稿恢复
- 菜谱删除后的计划快照展示
- 生成周计划 warning
- 菜篮手动新增
- 空态和失败态

### P2：可后置

- 分类拖拽排序

## 13. 协作机制

### 13.1 例会节奏

| 会议 | 频率 | 参与人 | 目标 |
| --- | --- | --- | --- |
| 站会 | 每日 15 分钟 | 研发、PM、QA | 同步进度、阻塞、当天目标。 |
| 需求澄清 | 每周 2 次或按需 | PM、设计、研发 | 解决需求歧义，冻结变更。 |
| 技术评审 | 每周 1 次 | 技术负责人、前后端 | 确认模型、接口、风险。 |
| 测试评审 | 第 2 周开始每周 1 次 | PM、QA、研发 | 确认测试用例和验收标准。 |
| 版本例会 | 提审前 | 全员 | 决定是否进入提审或延期。 |

### 13.2 需求变更机制

- P0 范围变更必须由 PM 和技术负责人共同确认。
- 已进入开发的需求，变更需要同步影响范围和延期风险。
- AI、月计划、运营后台默认不插入 MVP，除非替换掉同等工作量功能。

### 13.3 代码协作

- 主分支：`main`，保持可发布。
- 开发分支：`develop`，日常集成。
- 功能分支：`feature/recipe-edit`、`feature/week-plan`。
- 修复分支：`fix/basket-sync-merge`。
- PR 必须包含：变更说明、测试方式、截图或录屏。

## 14. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 微信登录/审核材料不完整 | 提审失败 | 第 0 周就确认协议、隐私、授权文案。 |
| 菜谱编辑页复杂度高 | 前端延期 | 先做无 AI、单图、固定三类食材，控制交互。 |
| 周计划生成效果不稳定 | 用户感知差 | 返回 warning，允许用户快速手动调整。 |
| 食材合并规则争议 | 菜篮不准 | MVP 只合并同名同单位，不做单位换算。 |
| 图片上传失败率高 | 创建菜谱受阻 | 前端压缩，后端明确错误码，允许无图保存。 |
| 范围膨胀 | 延期 | P0/P1/P2 管理，新增需求必须替换旧范围。 |
