# TASK-PLAN-API-001 日计划数据模型与接口

## 任务 ID

`TASK-PLAN-API-001`

## 背景

当前计划页已有日视图、三餐分区、添加菜谱、滑动删除和拖拽交互，但数据来自 `services/meal-plan-api.js` mock 和页面内存。MVP 要求计划写入时保存菜谱快照，且服务端必须做最终校验。

## 目标

实现日计划真实数据模型和服务端接口，让用户可以持久化查看、添加、移除指定日期三餐菜谱，并在写入时保存菜谱快照。

## 范围

### 包含

- 新增计划相关数据库迁移和回滚。
- 新增日计划读取接口/action。
- 新增添加菜谱到餐段接口/action。
- 新增移除餐段菜谱接口/action。
- 写入计划项时从服务端读取菜谱并生成快照。
- 所有数据按用户隔离。
- 单元测试或接口测试覆盖快照和删除原菜谱后的计划展示。

### 不包含

- 不实现周计划自动生成。
- 不实现菜篮同步。
- 不重写计划页 UI。
- 不做月计划。
- 不做 AI 自动菜单。

## 实现要求

- 数据模型至少支持：
  - `meal_plans`
  - `meal_plan_recipes`
  - `recipe_snapshot`
  - `source`
  - `sort_order`
- `recipe_snapshot` 至少包含菜名、封面、耗时、热量、食材、原菜谱 ID。
- `meal_type` 固定为 `breakfast`、`lunch`、`dinner`。
- 所有写操作必须使用服务端可信身份，不接受前端 userId。
- 日期参数必须校验。

## 前端设计保护

纯后端为主；如为验证补 service 映射，不改页面结构。

- 是否改 WXML：否
- 是否改 WXSS：否
- 是否改组件结构：否
- 是否保持现有字段契约：是
- 是否优先通过 `services/` 或数据映射接入：是
- 视觉回归范围：
  - 页面：计划页日视图
  - 弹窗：计划添加弹窗
  - 手势：滑动删除、长按拖拽
  - 空态/加载态/失败态：日计划空态、添加失败、移除失败

## API/数据变更

- 新增计划数据库表和回滚迁移。
- 新增服务端 action 或 API，建议对应：
  - 获取某日计划。
  - 添加菜谱到指定日期餐段。
  - 移除指定计划菜谱项。

## 验收标准

- [ ] 可创建并读取某日早餐、午餐、晚餐。
- [ ] 添加菜谱时保存菜谱快照。
- [ ] 移除餐段菜谱不影响原菜谱。
- [ ] 删除原菜谱后计划项仍可通过快照展示。
- [ ] 不同用户之间计划数据隔离。
- [ ] 参数非法时返回可展示错误。

## 测试要求

- [ ] 单元测试：快照生成、日期和 mealType 校验。
- [ ] 接口测试：读取、添加、移除、删除原菜谱后读取。
- [ ] 页面冒烟：可先不接页面，但需说明后续 `TASK-PLAN-FRONTEND-001`。
- [ ] 回归范围：后端迁移 up/down 或等价 SQL 检查。

## 风险

- 当前后端已有 AI 图库命名和 schema，新增计划表时要避免与现有 migration 冲突。
- 如果没有真实登录环境，需要使用后端测试 double 验证身份隔离。
