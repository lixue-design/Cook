# 全量 PRD 范围与实现规划

本文基于《菜谱小程序产品需求文档》revision `2054` 梳理 MVP 之后的剩余能力。当前目标从
「MVP 可用闭环」升级为「原始 PRD 全量能力」，但仍按 Harness Engineering 分阶段推进：
先补范围、spec、任务、验收，再逐个纵向切片实现。

## 1. 当前判断

### 1.1 已完成或接近完成的 MVP 主线

- 手动菜谱 CRUD、分类、详情、草稿和封面上传兜底。
- 日计划、周计划生成、计划项快照、手动调整。
- 周菜篮同步、同名同单位数字合并、勾选、手动新增、删除。
- 微信登录、我的页、协议/隐私、注销申请入口。
- 服务端 owner 隔离、写接口鉴权、迁移 0001-0014、基础诊断与发布清单。

这些能力仍需真实 CloudBase、微信登录、存储桶、真机/开发者工具和法务文案完成提审级验收。

### 1.2 原始 PRD 中尚未实现的主要能力

| 域 | 剩余能力 | 当前状态 |
| --- | --- | --- |
| 智能菜谱生成 | 链接生成菜谱、图片生成菜谱、文字生成菜谱 | MVP 入口提示未上线；首版统一走规则 provider，接口预留后续 AI provider。 |
| 智能菜品图库 | 菜名语义归一、同义词库、未命中生图预留、全局图库复用、运营后台 | 仅有本地图片搜索和方舟生图基础代码；首版先做规则匹配和运营闭环。 |
| 日计划增强 | 选择部分菜品同步菜篮、历史日计划永久回溯、一键复刻过往餐单 | 核心日计划已做；历史复刻和选择性同步未做。 |
| 月计划 | 月历视图、整月聚合、批量填充/清空/复用、全局替换、月度统计、模板 | MVP 明确裁剪；当前未做。 |
| 合规自动化 | 15 个工作日注销处理、数据删除/匿名化、协议版本强制更新确认 | 当前只有注销申请记录和静态协议入口。 |
| 列表加计划 | 菜谱卡片右下角「加计划」 | 原 PRD 中对应交互段落有删除线；需产品确认是否恢复。 |

## 2. 范围原则

- 不再把这些能力称为 MVP；统一称为 `Full PRD` 或 `post-MVP`。
- 每个能力都必须先有专项 spec、API 契约、任务卡、验证记录模板，再进入代码实现。
- Full PRD 执行必须遵守 `docs/harness/full-prd-team-and-harness-plan.md` 的人员分工、任务限制和样式门禁。
- 既有小程序前端样式不能更改；接新能力优先改 `services/`、页面 JS 数据映射和新增独立文件。
- 原 PRD 中涉及 AI 的能力首版全部使用本地/服务端规则生成；接口和任务模型预留 provider 抽象，后续可切换到 AI。
- 计划生成必须综合用户习惯、是否吃早餐、三餐差异、主食/蛋白质/蔬菜均衡、重复控制和日/周/月联动。
- 月计划不能挤进现有周计划页面的业务规则；需要独立 spec，复用现有日/周计划数据。
- 注销自动化涉及真实用户数据清理，只能在备份、审计、SLA 和人工复核规则明确后实现。
- PRD 中和现有快照模型冲突的条款不得直接实现，必须先做产品决策。

## 3. PRD 冲突与决策项

| 编号 | 冲突 | 推荐决策 | 原因 |
| --- | --- | --- | --- |
| D1 | 原 PRD 删除菜谱时提示「同步移出计划」，现有 MVP 采用计划/菜篮快照保留历史。 | 保持快照；删除原菜谱只标记原菜谱不可用。 | 保护历史计划和已采购记录，符合当前数据一致性约束。 |
| D2 | 原 PRD 月计划段落写在「周计划」章节内，且包含整月统计/模板。 | 独立建月计划模块。 | 避免周计划接口和页面过载。 |
| D3 | 原 PRD 新建入口有 AI 链接/图片/文字三种生成，MVP 当前提示未上线。 | 分三条纵向切片实现，共享生成任务模型；首版 provider=`rules`，后续预留 provider=`ai`。 | 三种入口输入、错误态不同，但不应一开始依赖模型服务。 |
| D4 | 原 PRD AI 图片优先级会自动覆盖上传原图；MVP 要求手动图优先。 | 手动上传图始终最高优先级；图库图和未来 AI 图只作为建议。 | 降低用户惊扰和审核风险。 |
| D5 | 原 PRD 要求完整注销自动清理，当前仅有申请。 | 先做申请状态机和审计，再做自动删除/匿名化任务。 | 真实数据删除不可逆，必须可追踪和可回滚。 |
| D6 | 原 PRD 周/月计划存在混写，且未细化日/周/月事实来源。 | 日级计划作为唯一事实表，周/月计划均为聚合或批量写入日级事实。 | 避免日、周、月三份数据互相冲突。 |

## 4. 阶段路线

### Phase 0：Full PRD Harness

- 建立全量 PRD 范围、专项 spec、任务队列、验收门禁。
- 更新 Context Map，让 Agent 后续按能力读取最小上下文。
- 输出执行顺序，避免 AI、月计划、合规清理并行互相踩数据模型。

### Phase 1：规则生成引擎与 provider 抽象

- 生成 provider：首版实现 `rules`，预留 `ai`。
- 异步生成任务：链接/图片/文字输入统一进入 job，前端轮询或订阅结果。
- 规则安全：外链格式、图片格式/大小、文本长度、输出 schema 校验。
- 习惯和计划规则：是否吃早餐、三餐偏好、耗时、忌口、主食/蛋白质/蔬菜均衡。
- 草稿回填：生成结果进入编辑页草稿，用户确认后再保存为正式菜谱。

### Phase 2：三种规则生成菜谱入口

1. 链接生成菜谱。
2. 图片生成菜谱。
3. 文字生成菜谱。
4. 前端入口恢复为可用状态，保留失败后手动录入兜底。

### Phase 3：规则菜品图库与运营

- 菜名标准化、同义词映射、图库命中复用。
- 未命中时先返回占位和运营待补状态；保留后续 AI 生图任务接口。
- 运营后台或最小运营页面：查看、替换、重新生成、维护同义词。
- 素材审核、质量状态、生成失败重试和回滚。

### Phase 4：日计划增强与月计划

- 日计划历史回溯和一键复刻。
- 按日/按菜品选择性同步菜篮。
- 用户习惯设置、营养均衡规则和三餐偏好进入计划生成。
- 月历视图聚合日/周计划，日级计划为唯一事实。
- 月度批量清空、复用、全局替换。
- 月度统计和月度模板保存/复用。

### Phase 5：合规自动化

- 注销申请状态机、处理 SLA、审计记录。
- 数据删除/匿名化任务，覆盖用户资料、菜谱、计划、菜篮、本地缓存提示。
- 协议版本管理和下次登录强制确认。
- 法务/产品复核后的提审验收。

### Phase 6：全量 PRD 验收与发布

- 从登录到 AI 生成、月计划、菜篮、注销的完整真实环境冒烟。
- 成本、日志、内容安全、权限和回滚演练。
- 更新提审运行手册和 PRD parity checklist。

## 5. 执行门禁

任何 Full PRD 任务完成前至少满足：

- 任务卡验收标准全部有结果。
- 涉及服务端写入时有单元或接口测试。
- 涉及 migration 时有 up/down 或等价验证记录。
- 涉及页面时有小程序冒烟记录，覆盖加载、空、失败、未登录、主流程。
- 涉及前端时必须证明未修改既有样式基线；新增页面必须复用现有设计语言。
- 涉及生成能力时必须有 provider=`rules` 测试、输出 schema 校验、失败兜底和未来 provider 切换边界。
- 涉及计划生成时必须覆盖用户习惯、三餐差异、营养均衡和日/周/月联动。
- 涉及注销/删除时有备份、审计、dry-run 和人工确认机制。

## 6. 下一步

从 `docs/tasks/full-prd-README.md` 中第一个 `Todo` 任务开始。默认顺序是先做规则生成引擎和 provider 抽象，再开放具体生成入口；月计划和注销自动化在数据模型稳定后推进。
